My initial X_eTaL-games collection

I would start with roughly this progression:

X_eTaL-games/
    games/
        horse-race/
        guess/
        tic-tac-toe/
        robot-chase/
        shut-the-box/
        connect-four/
        minesweeper/
        sudoku/
        trek/
        trek-adventure/
Tier 1 — tiny language demonstrations

Horse Race should be first. A vector holds every horse position; one expression advances selected horses; comparison against track length finds the winner. You can show the X_eTaL source alongside the 1970s-style APL.

Guess is useful mostly as a smoke test for game infrastructure: RNG, input, persistent state, messages and restart.

Tic-Tac-Toe is especially appropriate because you already explored TTT/TTTML in X_eTaL. A 3×3 board plus line extraction gives a beautifully small example, and later you can offer three opponents: random, minimax, and the existing ML approach.

Tier 2 — particularly array-ish games

Robot Chase may be the best real game demonstration. Represent the robots as either an N×2 coordinate matrix or occupancy matrix. Then each turn becomes approximately:

player position
robot positions
      ↓
direction/sign toward player
      ↓
all robot positions move simultaneously
      ↓
histogram / group duplicate positions
      ↓
robots sharing cells destroyed
      ↓
render occupancy matrix

That's a superb array-language example because vectorization is part of the game semantics: all robots really do move simultaneously.

Shut the Box demonstrates boolean masks and subset sums:

tiles      = 1..9
open       = boolean vector
roll       = d1 + d2
legal      = subsets(open tiles) whose sum = roll

That gives X_eTaL a completely different workload from a cellular automaton.

Connect Four is also unusually suitable: a 6×7 integer matrix, column insertion, and winner detection by extracting horizontal, vertical and two diagonal families. It is small enough that the entire rule engine ought to remain comprehensible on one screen.

Minesweeper is almost obligatory for an array language. Mine placement is a boolean matrix; adjacent-mine counts are essentially a neighborhood convolution. You already have the conceptual machinery from Life/CA demos.

Tier 3 — substantial demonstrations

Sudoku becomes the constraint/logic showcase.

A particularly nice X_eTaL representation would maintain:

board       9 × 9
candidates  9 × 9 × 9 boolean

Then eliminate candidates using broadcast masks across rows, columns and boxes. This is much more interesting for X_eTaL than simply translating the existing Rust solver line-for-line.

Star Trek then becomes the retro flagship. Your existing BASIC implementation already models the galaxy and sector maps explicitly and provides SRS/LRS, warp/impulse, phasers, torpedoes, shields, docking, etc.

I would call the X_eTaL version simply Trek rather than reproducing branding/artwork. Its terminal/grid aesthetic requires essentially no assets.

Other new games I think fit unusually well

Beyond those, I'd consider 2048, Lights Out, Mastermind, Reversi/Othello, 15 Puzzle, SameGame/Flood-It, Battleship, and Nim.

Of those, 2048 is probably the most compelling addition. A move is basically an array transformation:

orient board
→ remove zeros from each row
→ group/merge equal adjacent cells
→ pad with zeros
→ restore orientation

It makes a very nice demonstration of composition.

Reversi is somewhat larger but exceptionally array-oriented: directional rays from each empty square, masks for bounded opponent runs, flipping entire selected vectors.

Lights Out is even better pedagogically because the whole game can be expressed as operations over a binary matrix; eventually you can show the GF(2) linear-algebra solution next to interactive play.

Flood-It/SameGame adds connected-component/flood-fill operations, which exercises something quite different from the other games.

I would not initially add Pong, Breakout, Asteroids, platformers, etc. They're simple games in conventional languages, but most of the work becomes frame timing, collision geometry, keyboard state and rendering. They don't demonstrate why X_eTaL exists nearly as well as the board/puzzle/simulation games above.

Suggested implementation sequence

My order would therefore be:

Horse Race — tiny, historical, already APL.
Tic-Tac-Toe — tiny but genuine board game; connects directly to your existing X_eTaL/TTTML work.
Robot Chase — first really convincing vectorized game.
Shut the Box — masks/combinatorics/RNG.
Minesweeper — neighborhood/convolution operations.
2048 — array transformation/composition.
Connect Four — line/diagonal manipulation plus simple AI.
Sudoku — candidate tensor/constraint propagation.
Trek — larger flagship retro game.
Trek Adventure — state-machine/table-oriented counterexample showing X_eTaL isn't restricted to numerical grids.

That produces a much more interesting collection than ten arbitrary casual games: each one demonstrates a different array-programming technique.

What I would actually build for v0.1

I wouldn't start with ten games. I'd target six, chosen so that each answers a different question about X_eTaL:

Game	What it demonstrates
Horse Race	"Can X_eTaL express classic APL programs elegantly?"
Tic-Tac-Toe	"Can it express conventional board-game logic?"
Robot Chase	"What does simultaneous vectorized game state look like?"
Shut the Box	"How good is it at combinatorial/set-like problems?"
Minesweeper	"How good are neighborhood/grid calculations?"
2048	"Can array transformations directly model game mechanics?"

That's a very strong initial gallery because none is redundant.

Horse Race should probably be game #1

The provenance makes it unusually valuable:

original personal program
        ↓
APL reconstruction
        ↓
idiomatic APL
        ↓
X_eTaL

You could display all three implementations side-by-side.

The existing idiomatic APL is only 394 bytes, so there's also an interesting challenge: can the X_eTaL version be similarly concise while remaining more readable?

Robot Chase should be the flagship v0.1 game

Conceptually, I'd aim for something like:

robots : N × 2 coordinates
player : 1 × 2 coordinate

delta  ← sign(player - robots)
robots ← robots + delta

occupancy ← count-by-coordinate robots
wrecks    ← coordinates where occupancy > 1
robots    ← robots excluding wrecks

That is exactly the sort of computation where an array language should look dramatically better than a conventional imperative implementation.

v0.2: algorithms become opponents

Then I'd add:

Connect Four → Sudoku → Lights Out → Mastermind → Reversi

This introduces an important second dimension to the repo: games aren't just demonstrations of representation; they become demonstrations of algorithms written in X_eTaL.

That last one is especially valuable because the same game can compare:

v0.3: "array language superpowers"

I'd then deliberately choose games where a mathematical formulation becomes part of the exhibit.

Lights Out

Don't just implement clicking lights.

Have two modes:

    ordinary interactive Lights Out

SOLVE

    board → GF(2) system → solution vector

That makes it a miniature linear-algebra demo disguised as a game.

Sudoku

             candidate digit
                   ↓
          ┌─────────────────┐
          │ 9 × 9 × 9 bool │

That fits particularly well with the explanatory character you've already established in X_eTaL-demos.

The architectural rule I'd put in AGENTS.md is essentially:

If game rules can reasonably be expressed in X_eTaL, they MUST NOT be implemented in JavaScript.

JS should do things like:

mouse click → [row,column]
                    ↓
             X_eTaL move()
                    ↓
             new array state
                    ↓
              HTML renderer

rather than:

mouse click
     ↓
JavaScript implements game
     ↓
X_eTaL called somewhere
so we can call it an X_eTaL demo

That distinction will matter a lot as coding agents add games.

Common X_eTaL game API

I'd seriously consider standardizing a tiny protocol from the beginning:

new(seed)        → state
move(state, x)   → state
legal(state)     → moves
status(state)    → playing | won | lost | draw
view(state)      → display array

Optional:

score(state)     → number
ai(state)        → move
hint(state)      → move

That gives the JS harness essentially no knowledge of individual games.

For grid games, view could simply return an integer/character matrix and a little metadata. That means adding a new game can approach:

game.xtl
tests.xtl
manifest.json

rather than building another web application.
